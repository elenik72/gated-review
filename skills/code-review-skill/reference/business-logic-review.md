# Business logic review — does the change do what the ticket requires, and do it right

> Режим `business` (`finding.py init --mode business`). Технические находки здесь — только те, что
> меняют бизнес-результат; стиль в MR не идёт (лимит nit режима — 0). Механика заимствована и
> сверена 2026-09-30: проверка по тикету PR-Agent (уровень соответствия считает код), гейт качества
> задачи Kodus (без требований анализ не начинается), формат «требование — чего нет в коде — что
> сделать» CodeAnt/Kodus.

## 1. Без тикета бизнес-ревью нет

1. Достать тикет и соседние (эпик, связанные, ветка): Jira-скилл/MCP окружения, `glab`/`gh` для
   issue и описания PR, WebFetch. Недоступно — сказать это пользователю, а не ревьюить молча.
2. Оценить, есть ли в тикете требования: **пусто или одна строка** («сделать экран списка») — не
   продолжать, спросить у пользователя недостающее. Описание PR требованием не считается: его
   писал тот же автор, что и код.
3. Если пользователь подтверждает, что тикета нет, — `finding.py render --no-ticket "<почему>"`:
   причина попадёт в сводку Phase 4, и отсутствие проверки будет видно.

## 2. Требования — дословно, по одному

```bash
F=<skill>/scripts/finding.py      # <skill> — каталог SKILL.md
python3 "$F" req --add "открытие нового оверлея закрывает предыдущий" --source "SPH-1184 AC2"
python3 "$F" req --add "пустой список показывает пустое состояние с кнопкой «Обновить»" --source "SPH-1184"
```

- Цитата, не пересказ: пересказ теряет условие, которое автор и пропустил.
- Отдельной строкой — **инварианты** («недоступный сервис не читается как ноль», «один
  активный запуск на игрока»), **исключения** («кроме заблокированных»), **роли** («только
  тимлид»), **граничные значения** («не больше 100», «с 00:00 по МСК»). Их реализации пропускают
  чаще всего.

## 3. Статус каждого требования — с доказательством

| Статус | Когда | Что обязательно (`req --mark R<n> --status …`) |
|---|---|---|
| `met` | реализовано, и есть проверка, которая могла бы опровергнуть | `--where file:line`, `--evidence "<тест или grep>" --output "<вывод>"` |
| `partial` | реализовано не всё | `--where`, `--why` — чего именно нет |
| `missing` | реализации нет | `--evidence "git grep -n <что должно быть>" --output "<пусто / не то>"` |
| `unverified` | по коду не проверить (UI, стенд, данные прода) | `--why` — пункт уходит человеку, **не** в MR |

Уровень соответствия считает `finding.py` (не модель): всё `met` — «полностью соответствует»;
есть `missing`/`partial` — «частично» или «не соответствует»; есть только `unverified` сверх `met` —
«код соответствует, нужна проверка человеком». `render` откажет, пока у требования нет статуса.

Каждое `missing` и `partial` становится находкой формы `unimplemented` с той же цитатой; каждое
`met` с тестом на ступени 3 — лучший способ закрыть требование без спора.

## 4. Правильно ли реализовано — классы бизнес-ошибок

| Claim | The free check that could kill it | It dies when |
|---|---|---|
| `граница <N> включена/исключена не так, как в требовании` | (1) найти сравнение (`<`/`<=`, `between`, срез); (4) тест на N−1, N, N+1 | тикет говорит «не больше» и код `<=`; тест на границе есть и зелёный |
| `сумма округляется/складывается с потерей копеек` | (1) тип по цепочке модель → схема → ответ; (4) repro 0.1+0.2 / 1/3 | Decimal/целые копейки на всём пути, округление по правилу тикета |
| `период/дата считается в чужом часовом поясе` | (1) откуда `now()`, в каком поясе граница суток из тикета; (4) тест на 23:59 и 00:01 | aware-время в поясе из требования на всём пути |
| `переход <A → B> разрешён, хотя тикет его запрещает` (или наоборот) | (1) все места, где меняется статус: `git grep -n "status ="`; есть ли проверка текущего состояния | переходы идут через одну функцию с явным списком разрешённых |
| `повтор запроса/задачи создаёт дубль <сущности>` | (1) ключ уникальности, UPSERT/`get_or_create`, idempotency key; (4) двойной вызов в тесте | уникальный индекс или идемпотентный ключ на операции |
| `роль <R> может то, что тикет ей запрещает` | (1) проверка прав в обработчике/сервисе, не только в UI; (4) вызов под ролью без прав | проверка на сервере на этой операции |
| `«нет данных» показывается как ноль (или наоборот)` | (1) ветка ошибки/недоступности: что уходит в ответ и в UI | ошибка и пустота различимы в ответе и на экране |
| `агрегат считается по отфильтрованной выборке, а тикет говорит «всего»` (или наоборот) | (1) откуда берутся строки для суммы/счётчика — та же выборка, что показывается? | популяция агрегата совпадает с требованием |
| `поведение, которого не требует тикет: <что>` (форма `unrequested`) | (1) поиск по тикету и соседним: `grep -i <термин>`; решения/обсуждения в тикете | требование или принятое решение его называет; тогда это не находка |

`unrequested` по умолчанию 🟢, 🟡 — если меняет видимое пользователю поведение или данные: такое
поведение никто не проверит при приёмке.

## 5. Что выходит из ревью

- `finding.py stats` печатает таблицу требований и уровень — её вставить в сводку Phase 4 как есть.
- `unverified` — отдельным списком «проверить руками» для автора или QA, в MR не постится.
- Вердикт: хотя бы одно `missing` для безопасности или целостности данных — 🔄 Request Changes.
